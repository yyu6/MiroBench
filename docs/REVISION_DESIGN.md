# 高效修订层设计 — 2026-08-29

## 0. 先说结论

**你提的三个方案里,前两个已经被实测否掉,第三个是对的方向但要改一处关键设计。**

| 方案 | 判断 | 依据 |
|---|---|---|
| writer 阶段一直重试 | **已测,反效果** | G88 |
| writer 阶段跑 ensemble / best-of-N | **同源,大概率同样反效果** | G88 + 成本 |
| **写完打分 → 针对性改** | **对,但选择粒度要改成"pair"而不是"comment"** | 见 §3 |

---

## 1. 为什么"writer 一直重试"不行 — 这是实测过的

**G88**:`--writer-retries 1` 是一个写时改写守卫,付费 N=10 跑过。

```
38% 的 slot 被重写（202/532），0 个降级
self_bertscore  +4.33% → +5.09%   变差
self_bleu_4    +18.85% → +20.54%  变差
```

而且它**在自己的目标上也失败** —— 重写后的语义收敛度并没有改善。

**原因**:重试是"再写一次",而模型的输出分布没变。第二次抽样和第一次来自同一个分布,平均下来不会更分散。

**best-of-N 是同一个问题的放大版**:N 次抽样都来自同一分布,选最好的那个是在**抽样噪声里挑**,不是在改分布。而且成本是 N 倍。

## 2. 一个必须先说清楚的事实

**G145**:缺陷是语料级的。

```
real   跨thread 0.4857   thread内 0.5041   （thread效应 +0.0184）
v128   跨thread 0.5241   thread内 0.5409   （thread效应 +0.0168）
```

我们**任意两条来自不同帖子的评论**已经 +0.038 太像,而"同处一个 thread 额外增加的相似度"我们比 real 还小。

**这意味着:一个 thread 内的 reviser 能把指标改下来,但它改的不是病因。** 它是在直接优化那个数字。

- 机制上:有效。指标是 thread 内算的,你把 thread 内的评论改得互相不像,数字就降。
- 科学上:这是 metric-targeted optimization。`docs/ORIENTATION.md` §1 禁止的正是这个。
- 论文上:声明会从 "first-pass generation" 变成 "first-pass + metric-targeted revision"。

**这是你的决定。我把代价说清楚,然后给最高效的做法。**

## 3. 推荐设计:pair 级、单轮、批量、代理选择

### 3.1 核心改动 — 选 pair,不选 comment

现有的 reviser(`postprocess_selfbleu_lexical_reviser.py`)选的是**评论**:"这条评论对超标贡献最大,重写它"。

**应该选 pair**:"这两条评论共享的措辞太多,把其中一条改得不像另一条"。

理由:
- 指标本身就是 pairwise 的。选 pair 是直接对着目标函数操作
- 模型拿到的是一个**具体的对比**("别像这条"),不是一个抽象要求("多样化一点")。**E4** 测过:指定具体 token 服从率 ≈ 1.0,指定类别只有 0.23
- v134 的失败正是因为它给的是抽象清单("这些词组别用"),Writer 照说不误

### 3.2 用便宜的代理选,用真指标验一次

**BERTScore 是时间瓶颈** — CPU 上 deberta-xlarge,每个 thread 内所有评论两两算。N=150 时这一步以小时计。

设计:
```
选择阶段：2-gram Jaccard      毫秒级，纯 Python，无模型
修订阶段：k 次批量 LLM 调用
验证阶段：真 BERTScore，整轮结束后跑一次
```

代理和真指标的排序相关性我正在测(`proxy.py`)。如果 Spearman ρ > 0.6 且 top-10% 重合率 > 0.5,这个代理就够用来做选择。

### 3.3 一轮,不迭代

每一轮 accept/reject 都要重新打分,成本翻倍。改成:
- 修订后只检查**硬约束**(anchor 保留、长度桶、无泄漏),不检查指标是否改善
- 整批跑完后用真指标验一次
- 不回头

理由:accept/reject 循环本质上是在做 best-of-N,而 §1 说了那是无效的。

### 3.4 批量调用 — 最大的墙钟收益

一次调用改 k 条,不是 k 次调用。附带好处:模型能看到它同时在改的其他几条,**自然会把它们写得不一样**。

⚠️ **踩过的坑**:批量时 token 预算要按 k 条算。我第一次试给 8 条评论只留 400 token,24/45 条被截断成空的,数字全废。

## 4. 成本估算(N=150)

假设 ~150 threads、~8000 comments、每 thread 改 k=3 对。

| | 调用数 | 相对生成的开销 |
|---|---|---|
| 生成 | ~8000 | — |
| 选择(代理) | 0 | 0 |
| 修订(批量,每 thread 1 次) | ~150 | **+1.9%** |
| 最终验证(真指标) | 0 LLM | 一次评测 |

**关键**:k 的取值由 `revbudget.py` 决定 —— 它在算"只改 top-k 条能拿回多少 gap"。如果 top-3 能拿回 60%,就不需要改 10 条。

墙钟增加约 10%(修订调用可以跨 thread 并行)。

---

## 5. 我不推荐的做法,和理由

| 做法 | 为什么不 |
|---|---|
| 每条评论写完就打分 | 打分需要 thread 内其他评论,写第 1 条时没有对照。而且 N 次打分 = N 倍成本 |
| 12 个指标全都修 | 10 个已经 PASS。修它们只会引入回归。**只修 self_bertscore 和 self_bleu_4** |
| 多轮迭代直到达标 | 就是 best-of-N,G88 已证否,且成本不可控 |
| 用 BERTScore 做选择 | CPU 瓶颈,N=150 时以小时计 |

## 7. 旧 reviser 慢在哪 — 量化,不是印象

`card_deepseek_v4_flash_v37_auto_150_20260723_v3_selfbleu_selfloop_round01_high_tail` 的自有报告:

```
选中 thread            79
LLM 调用               431
成功应用的 thread       59   (75%)
被接受的改写            69
每个成功改写的调用数     6.2   ← 84% 的调用被丢弃
无一改写被接受的 thread  19   (24%)  ← 调了 LLM，全拒，纯浪费
```

**而且这条线跑了 7 轮**(`artifacts/*selfbleu_selfloop_round01..07`,共 71 个目录)。

`431 × 7 ≈ 3017` 次调用。

### 对照本设计

| | 旧 | 新 |
|---|---|---|
| accept/reject 循环 | 6.2 次调用换 1 次成功 | 不检指标,只检硬约束 → 1 次 |
| 轮数 | 7 | 1 |
| 调用粒度 | 每条评论 1 次 | 每 thread 1 次批量 |
| **79 个 thread 的总调用** | **~3017** | **~79** |

**约 38 倍。**

这三条改动各自的依据都在 §3,而这里给出它们合起来值多少。

**注**:那批 card 的 self-loop 用的就是 DeepSeek(`card_deepseek_v4_flash`),所以 DeepSeek 在这条 pipeline 上是有先例的。
